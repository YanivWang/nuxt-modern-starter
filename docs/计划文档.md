# Nuxt 项目基础骨架 Implementation Plan（收敛修复版）

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 搭建一个可复用、可裁剪、适合官网/海外站/营销页/SEO 页面/轻 SaaS 前台的现代 Nuxt 项目基础骨架；v0.1 先交付可运行、可验证、可裁剪的核心模板，生产增强项分阶段收口。

**Tech Stack:** Nuxt 4, TypeScript, pnpm, Pinia, Ant Design Vue, SCSS, `vue-i18n`, Vitest, ESLint, Prettier, stylelint, husky, commitlint, Nitro, Docker, Nginx. Docker/Nginx 样例和实跑验证全部归入 v0.1；Playwright E2E 和远程 CI 不做。

## 1. 骨架定位

这个骨架不做成"空白 Nuxt starter"，而是做成一个能支撑真实项目开局的企业级基础框架。

适用场景：

- 海外官网
- 营销落地页
- SEO 页面
- 多语言内容站
- 产品价格页
- 帮助中心/文档站
- 轻 SaaS 前台
- 需要 SSR 首屏数据的公开页面

不作为第一目标的场景：

- 重后台管理系统
- 大型低代码平台
- 强实时协作编辑器
- 强业务绑定的会员/支付/积分系统
- 特定公司私有 SDK 强依赖项目

骨架原则：

- 基础能力稳定，业务能力可插拔。
- 目录清晰，页面只做组装。
- 请求、SEO、多语言、环境变量统一出口。
- 默认可运行，可裁剪，可迁移。
- 首版少而稳，后续按项目反馈扩展。

首版范围：

- v0.1 只做可验证的官网/营销页最小闭环，不追求一次性覆盖所有企业门户页面。
- v0.1 必做页面：`/`、`/pricing`、`/help`、`/news`、`/news/[slug]`、`/[...slug]`，实际文件采用 `app/pages/[[language]]/...` 结构以匹配多语言前缀。
- v0.1-core 必做能力：配置中心、布局、i18n、轻量请求入口、SEO 产物、routeRules、基础工程质量、基础文档、Docker/Nginx 部署样例和实跑验证。
- v0.1 不启用 auth、analytics、CMS、支付、上传、复杂会员能力。
- auth 只保留文档级扩展边界，不创建运行时代码占位；analytics、CMS、支付、会员、上传、更多语言、Playwright E2E、远程 CI 不进入本计划。

## 2. 项目命名

```txt
nuxt-modern-starter
```

项目名已确定为 `nuxt-modern-starter`。该命名不绑定单一业务品牌，也不限制在海外营销站场景，适合后续作为通用 Nuxt 基础骨架长期维护。

版本决策：

- 新骨架直接使用 Nuxt 4，不做 Nuxt 3 兼容模板。
- 目录结构采用 Nuxt 4 默认推荐的 `app/` 分层。
- 从 `aippt-home` 参考经验时，只吸收请求、SEO、多语言、错误页、部署等通用实践，不沿用 Nuxt 3 时代的目录和历史包袱。
- 如果旧项目要迁移到该骨架，按"业务迁移到 Nuxt 4 骨架"的方式处理，而不是让骨架回退兼容旧项目。

### 3.2 UI 方案

UI 方案确定为：

```txt
Ant Design Vue + SCSS
```

选择理由：

- 与 `aippt-home` 现有组件体系和团队经验更贴近。
- 适合官网/营销页里常见的按钮、表单、弹窗、下拉、语言切换等基础交互。
- v0.1-core 只维护一套 UI，避免模板同时背负多套组件库、样式变量和 SSR 接入方式。
- v0.1-core 内置 light/dark 两套基础 design token，先解决品牌色、背景、文字、边框、圆角、阴影、间距、字体等跨页面一致性；不做完整 Figma 级组件 token 系统。

不再为 v0.1 规划 Element Plus 分支；如果未来确实需要另一套 UI，应作为独立模板项目重新评估，而不是混入 `nuxt-modern-starter`。

## 5. 核心模块设计

### 5.1 环境配置模块

目标：

- 所有环境变量从 `runtimeConfig` 进入项目。
- 业务代码不直接读取 `process.env`。
- 明确区分服务端私有配置和客户端公开配置。
- 明确 `runtimeConfig`、`app.config.ts`、`config/*.ts` 的职责边界。

建议配置：

```ts
export default defineNuxtConfig({
  runtimeConfig: {
    apiSecret: "",
    public: {
      appEnv: "",
      apiBase: "",
      siteUrl: "",
      assetsBase: "",
    },
  },
});
```

环境文件：

```txt
.env.dev
.env.test
.env.prod
```

脚本：

```json
{
  "scripts": {
    "dev": "nuxt dev --dotenv .env.dev",
    "dev:test": "nuxt dev --dotenv .env.test",
    "build": "nuxt build --dotenv .env.prod",
    "build:test": "nuxt build --dotenv .env.test",
    "preview": "nuxt preview"
  }
}
```

生产运行时规则：

- `.env.dev`、`.env.test`、`.env.prod` 只作为本地开发和构建脚本的输入。
- 构建后的 Nuxt server 启动时不会自动读取项目根目录 `.env`。
- 生产环境必须通过部署平台、容器或进程管理器注入 `NUXT_*` 环境变量。
- `runtimeConfig` 中的字段必须先在 `nuxt.config.ts` 声明，才能被运行时环境变量覆盖。
- 私有配置使用 `NUXT_API_SECRET` 这类服务端变量；客户端公开配置使用 `NUXT_PUBLIC_API_BASE`、`NUXT_PUBLIC_SITE_URL` 这类变量。
- 业务代码不读取 `process.env`，统一通过 `useRuntimeConfig()` 或 server runtime config 读取。

环境变量命名示例：

```txt
NUXT_API_SECRET=server-only-secret
NUXT_PUBLIC_APP_ENV=production
NUXT_PUBLIC_API_BASE=https://api.example.com
NUXT_PUBLIC_SITE_URL=https://example.com
NUXT_PUBLIC_ASSETS_BASE=https://cdn.example.com
```

验收标准：

- 新项目 clone 后使用已提交的 `.env.dev` 即可启动。
- 切换环境只需要换脚本或 dotenv 文件。
- `runtimeConfig.public.apiBase` 能在客户端和服务端稳定读取。
- README 明确说明本地 `.env.*` 和生产 `NUXT_*` 的区别。
- 生产预览文档中不要求依赖 `.env.prod` 自动生效。

### 5.1.1 配置职责边界

三类配置必须分清，避免后续项目把密钥、品牌、SEO、导航都塞进同一个地方。

| 配置位置            | 放什么                                                    | 不放什么                               | 示例                                                    |
| ------------------- | --------------------------------------------------------- | -------------------------------------- | ------------------------------------------------------- |
| `runtimeConfig`     | 部署环境相关、运行时可变、可能私密的配置                  | 主题色、导航、页面文案、design token   | `apiSecret`、`public.apiBase`、`public.siteUrl`         |
| `app/app.config.ts` | 非私密、偏 UI/品牌/主题、客户端可读取且可响应式更新的配置 | API 密钥、服务端私有配置、环境变量直读 | `brandName`、`theme.defaultMode`、`layout.headerFixed`  |
| `config/*.ts`       | 静态业务配置源，供页面、SEO、sitemap、导航、主题复用      | 需要部署时动态覆盖的密钥               | `siteConfig`、`navConfig`、`seoDefaults`、`themeTokens` |

推荐规则：

- 只要跟部署环境有关，优先进入 `runtimeConfig`。
- 只要可能包含密钥，只能放在 `runtimeConfig` 私有字段或服务端代码中。
- 只要是品牌展示、默认主题模式、layout 开关，优先进入 `app.config.ts`。
- 只要是成体系的 design token，优先进入 `config/theme.ts`，再同步生成 SCSS/CSS variables 和 Ant Design Vue token 映射。
- 只要是站点结构、导航、SEO 默认值，优先放在 `config/*.ts`，再由 composable 或 server route 消费。
- 页面组件不直接读取 `process.env`，也不硬编码站点域名。

验收标准：

- 项目创建 `app/app.config.ts`，至少包含品牌名、默认主题模式、layout 基础开关。
- 项目创建 `config/theme.ts`，集中维护 light/dark design token，不在页面和组件中散落硬编码颜色。
- `nuxt.config.ts` 只声明 runtimeConfig 和 Nuxt/Nitro 配置，不塞业务导航和大段页面文案。
- `docs/conventions.md` 解释三类配置的放置规则。
- `docs/usage.md` 给出新增配置时的判断流程。
- 提供轻量运行时配置校验：缺少 `runtimeConfig.public.siteUrl`、`runtimeConfig.public.apiBase` 等关键值时，在 dev/build 文档中说明预期降级或报错方式。

### 5.1.2 主题与 design token 模块

目标：

- v0.1-core 内置明暗两套基础 design token。
- 自研页面样式、基础组件和 Ant Design Vue 使用同一份主题源。
- 主题模式可以跟随系统，也可以手动切换并持久化。
- 避免页面里散落硬编码颜色、阴影、圆角和字体尺寸。

token 来源：

```txt
config/theme.ts
app/assets/styles/tokens.scss
app/composables/useTheme.ts
app/stores/theme.ts
```

推荐 token 分层：

| 层级              | 示例                                                                 | 说明                                                                 |
| ----------------- | -------------------------------------------------------------------- | -------------------------------------------------------------------- |
| primitive token   | `colorBlue600`、`colorGray950`、`space4`、`radiusMd`、`fontSizeBase` | 原始色阶、间距、圆角、字号、阴影，不直接表达业务语义                 |
| semantic token    | `colorBgPage`、`colorTextPrimary`、`colorBorder`、`colorLink`        | 页面和组件优先消费语义 token，而不是直接消费 primitive token          |
| component mapping | `buttonPrimaryBg`、`headerBg`、`cardBg`                              | 只覆盖 starter 基础组件需要的轻量组件 token，不做完整组件 token 系统 |
| Ant Design mapping | `colorPrimary`、`colorBgBase`、`colorTextBase`、`borderRadius`       | 映射到 Ant Design Vue theme token，保证第三方组件和自研样式观感一致   |

主题模式：

| 模式      | 行为                                                                 |
| --------- | -------------------------------------------------------------------- |
| `system`  | 默认模式，读取 `prefers-color-scheme`，SSR 首屏先使用默认 light token，客户端 mounted 后同步系统偏好 |
| `light`   | 强制浅色主题，并持久化到 localStorage                                 |
| `dark`    | 强制深色主题，并持久化到 localStorage                                 |

实现约束：

- `config/theme.ts` 导出 `lightThemeTokens`、`darkThemeTokens`、`themeTokenMap` 和 Ant Design Vue token 映射函数。
- `app/assets/styles/tokens.scss` 暴露 `:root[data-theme="light"]` 和 `:root[data-theme="dark"]` 的 CSS variables。
- `app/stores/theme.ts` 只维护 `mode`、`resolvedMode`、`setMode()`、`toggleMode()`，不绑定具体业务页面。
- `useTheme.ts` 负责初始化主题、监听系统主题变化、写入根节点 `data-theme`，并给 Ant Design Vue ConfigProvider 提供 token。
- Header 提供轻量主题切换入口，但不把主题切换写死在业务组件里。
- 文档必须说明新增 token 的命名规则、使用优先级和裁剪方式。

验收标准：

- light/dark 两套主题下首页、价格页、帮助页、新闻页、404 页可读、对比度合理，无明显闪烁或横向溢出。
- 自研样式优先使用 CSS variables，不在页面组件中直接写品牌色、背景色和正文色。
- Ant Design Vue 的主色、背景、文字、圆角至少由项目 token 映射控制。
- 主题切换状态可持久化，刷新后保持用户选择。
- `docs/conventions.md` 写明 design token 分层、命名和新增规则。
- `docs/usage.md` 写明如何改品牌色、关闭暗色主题或删除主题切换入口。

### 5.2 请求模块 `useApi`

目标：

- 统一替代零散的 `useFetch`、`$fetch`、自定义 request。
- 明确 SSR 首屏请求和客户端交互请求的区别。
- 自动注入 token。
- 统一错误结构。
- 支持服务端直连 API，客户端走同源或网关。

推荐 API：

```ts
const { data, error, pending, refresh } = await useApi<ResponseData>("/api/user/info", {
  key: "user-info",
  method: "GET",
  server: true,
});
```

> **核对说明：** `server` 是 Nuxt 官方 `useFetch` 的 `UseFetchOptions` 类型中真实存在的字段，用于控制该请求是否在 SSR 阶段执行（已核对：https://nuxt.com/docs/api/composables/use-fetch）。`useApi` 在这里是对官方选项的语义包装，不是自造概念。

使用规则：

| 场景            | 推荐写法                                           | 原因                                |
| --------------- | -------------------------------------------------- | ----------------------------------- |
| 首屏 SSR 数据   | `await useApi(url, { server: true })`              | 进入 Nuxt payload，避免水合重复请求 |
| 客户端按钮/表单 | `useApi(url, { server: false, immediate: false })` | 用户操作触发                        |
| 服务端聚合接口  | `server/api/*` + `$fetch`                          | 隐藏密钥、聚合多接口                |

实现约束：

- `useApi` 基于 Nuxt 数据层实现，首屏数据优先包装 `useFetch` 或 `useAsyncData`，不要另起一套绕开 payload 的 SSR 请求机制。
- 显式传入 `key` 时，同一个 key 不允许搭配不同的请求 URL、transform、pick、default、deep 等关键选项。**这不是 `useApi` 自造的限制，而是和官方行为一致：`useFetch`/`useAsyncData` 在同 key 但配置不一致时会在开发环境触发警告**（已核对：https://nuxt.com/docs/api/composables/use-async-data）。
- 未传 `key` 时，由 method、path、query/body 摘要和 locale 生成稳定 key，避免不同页面意外复用同一份数据。
- `server: true` 的请求必须能进入 Nuxt payload；客户端 hydration 不应再次发起同一首屏请求。
- 服务端请求允许读取私有 `runtimeConfig`；客户端请求只能读取 `runtimeConfig.public`。
- **服务端发起外部 API 请求时，必须明确是否转发 cookie、authorization、accept-language、x-forwarded-\* 等 header；默认只转发安全白名单。这一条不是可选优化，而是安全底线**：Nuxt 官方 `useRequestFetch` 文档说明，`useFetch` 在服务端会使用 `useRequestFetch` 转发当前请求上下文和 headers（已核对：https://nuxt.com/docs/4.x/api/composables/use-request-fetch）。因此 `useApi` 必须区分“请求本站 server/api 的相对路径”和“请求外部 API 的绝对地址”：前者可保留 Nuxt 默认上下文转发，后者必须显式过滤 header，防止把用户 cookie 或 authorization 透传给不该收到的第三方服务。
- token 获取和注入只在 `useApi` 或后续 `useAuth` 内部集中处理，页面不能手写 token header。
- API 错误统一归一为 `ApiError`，但日志里的 `raw` 错误不能泄露 token、cookie、密钥或完整服务端堆栈到客户端。

错误结构：

```ts
interface ApiError {
  statusCode: number;
  message: string;
  code?: string | number;
  raw?: unknown;
}
```

验收标准：

- 项目中只有一个推荐请求入口。
- 请求 key 规则稳定，SSR 和 hydration 不重复拉取首屏数据。
- 同 key 不会出现不同请求配置混用。
- SSR 请求和客户端请求的 baseURL、header、token 行为有测试覆盖，**测试用例必须包含"白名单外的 header 确实没有被转发"这一条**，不能只测试"白名单内的 header 被正确转发"。
- token 注入逻辑集中维护。
- 错误处理可以统一接入 toast、日志、跳登录。

### 5.3 多语言模块

目标：

- 翻译能力使用 `vue-i18n`，不使用 `@nuxtjs/i18n`。
- 国际化结构参照 `/Users/wangcheng/Documents/workSpace/frontEnd/pixelBloomSpace/oversea/aippt-home` 的 `i18n/index.ts`、`plugins/i18n.ts`、`middleware/default.global.ts`、`store/language.ts`。
- 默认语言不带前缀。
- 非默认语言带语言前缀。
- 提供统一路径生成函数。
- 自研语言路由归一化，避免把路由策略绑定到第三方 Nuxt i18n 模块。

路由示例：

```txt
/
/pricing
/help
/en/pricing
```

推荐封装：

```ts
const path = localePath("/pricing");
const target = switchLocalePath("en-US");
```

模块边界：

| 能力                         | 归属                         | 说明                                                               |
| ---------------------------- | ---------------------------- | ------------------------------------------------------------------ |
| 文案翻译、插值、fallback     | `vue-i18n`                   | `i18n/index.ts` 创建实例，中文常驻加载，英文按需加载；v0.1-core 不内置更多语言 |
| 支持语言清单、默认语言、前缀 | `i18n/index.ts`              | 参照 `aippt-home` 的 `LOCALE_LANGUAGE_MODULES`、`SITE_LANG_MAP`、`STORAGE_KEY_LANGUAGE`；starter 中每个 locale 必须显式声明 `pathPrefix` |
| 语言包组织                   | `i18n/<locale>/index.ts` + `modules/*.json` | 每个 locale 的 `index.ts` 聚合 `global`、`home`、`news`、`pricing`、`help` 等模块 |
| 默认语言无前缀               | `app/middleware/locale.global.ts` | 参照 `aippt-home` 的规则，但将默认语言改为中文：`/zh`、`/zh/...` 301 到无前缀路径 |
| 非默认语言前缀               | `app/pages/[[language]]/...` + middleware | 页面文件用 `[[language]]` 匹配语言段，middleware 校验语言是否合法   |
| 路径生成和语言切换           | `useLocalePath.ts` + `app/stores/language.ts` | 参照 `relativeLangPath()`、`getSwitchLanguageUrl()`，页面禁止手写语言前缀 |
| hreflang / sitemap URL       | SEO 模块 + `i18n/index.ts`   | 使用同一份语言映射生成 alternate 和 sitemap URL                    |

默认语言策略：

- `zh-CN` 为默认语言。
- v0.1-core 只支持 `zh-CN` 和 `en-US`。
- `/zh` 自动 301 到 `/`。
- 非法语言前缀返回 404。

> **实现说明：** 使用 `vue-i18n` 后，不再存在 `@nuxtjs/i18n` 的 `strategy: 'prefix_except_default'` 配置。默认语言不带前缀、非默认语言带前缀、默认语言短前缀 301、非法语言前缀 404，都必须参照 `aippt-home` 的 `i18n/index.ts` 和 `middleware/default.global.ts` 明确实现并测试，但默认语言从 `aippt-home` 的英文调整为中文。`aippt-home` 里的登录后跳工作台、后台语言列表、埋点上报属于业务逻辑，starter 不照搬。

路由归一化矩阵：

| 输入路径              | 期望行为                  | 状态码     | 说明                                |
| --------------------- | ------------------------- | ---------- | ----------------------------------- |
| `/`                   | 渲染中文首页              | 200        | 默认语言不带前缀                    |
| `/pricing`            | 渲染中文价格页            | 200        | canonical 指向 `/pricing`           |
| `/zh`                 | 重定向到 `/`              | 301        | 默认语言短前缀不保留                |
| `/zh/pricing`         | 重定向到 `/pricing`       | 301        | 默认语言页面统一无前缀              |
| `/en`                 | 渲染英文首页              | 200        | 非默认语言带短前缀                  |
| `/en/pricing`         | 渲染英文价格页            | 200        | 非默认语言带短前缀                  |
| `/fr/pricing`         | 返回 404                  | 404        | 如果 `fr` 未配置为支持语言          |
| `/unknown-page`       | 渲染多语言 404            | 404        | 不能返回 200 假 404                 |
| `/en/unknown-page`    | 渲染英文 404              | 404        | 保留语言上下文                      |
| `/pricing/?a=1#faq`   | 归一为 `/pricing?a=1#faq` | 301 或 200 | 尾斜杠策略必须明确且不丢 query/hash |

验收标准：

- 页面内不手写语言前缀拼接。
- Header、Footer、按钮跳转全部使用 `localePath`。
- 语言切换保留当前 path、query、hash。
- 默认语言重定向、非法语言 404、catch-all 404 不互相覆盖。
- 不照搬 `aippt-home` 中通过 locale 后半段推导 URL 前缀的隐式规则；starter 必须用显式 `pathPrefix`，例如 `zh-CN -> zh`、`en-US -> en`，其中默认语言 `zh-CN` 的前缀只用于识别和重定向，不作为 canonical URL。
- v0.1-core 的 `LOCALE_LANGUAGE_MODULES` 和 `SITE_LANG_MAP` 只包含中文和英文；更多语言不进入本计划。

测试要求：

- `localePath()` 覆盖默认语言无前缀、非默认语言有前缀、query/hash 保留和尾斜杠归一。
- `switchLocalePath()` 覆盖从 `/pricing?a=1#faq` 切到 `/en/pricing?a=1#faq`，以及从 `/en/news/demo` 切回 `/news/demo`。
- `locale.global.ts` 覆盖 `/zh`、`/zh/pricing`、`/en`、`/en/pricing`、`/fr/pricing`、`/unknown-page`、`/en/unknown-page`。
- SSR 首屏 locale 初始化必须验证 HTML、SEO meta、hreflang 和页面文案使用同一语言上下文。
- 非法语言前缀、普通业务 404、catch-all 404 必须分别验证状态码，避免出现 200 假 404。

### 5.4 SEO 模块

目标：

- 页面 SEO 写法统一。
- 默认站点信息集中维护。
- 支持 canonical、OG、Twitter Card、多语言 alternate。
- 生成可上线的 SEO 基础产物，而不仅是页面 meta。

推荐调用：

```ts
usePageSeo({
  title: "Pricing",
  description: "Choose the plan that fits your team.",

```

配置文件：

```ts
export const siteConfig = {

  defaultOgImage: "/og/default.png",

```

验收标准：

- 每个公开页面有 title、description、canonical。
- 多语言页面有正确 alternate。
- 不在页面中重复硬编码站点域名。
- 生成 `robots.txt`，并能按环境区分是否允许索引。
- 生成 `sitemap.xml`，包含默认语言和非默认语言公开页面。
- 404、预览类页面默认 `noindex`。
- 新闻/文章详情页支持 JSON-LD 基础结构化数据。

SEO 产物边界：

| 产物                           | v0.1 要求 | 说明                                                                                                                                                                                         |
| ------------------------------ | --------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `usePageSeo`                   | 必做      | 页面 title、description、canonical、OG、Twitter Card                                                                                                                                         |
| `hreflang`                     | 必做      | 多语言 alternate 统一由 SEO 模块生成                                                                                                                                                         |
| `server/routes/sitemap.xml.ts` | 必做      | 基于站点配置和 typed 本地数据生成 `sitemap.xml`                                                                                                                                              |
| `server/routes/robots.txt.ts`  | 必做      | production 允许索引，非 production 默认禁止                                                                                                                                                  |
| JSON-LD                        | 轻量必做  | 文章/新闻详情页提供基础 `Article` 示例；**`Organization`、`WebSite` 两类结构化数据不进入 v0.1，但在 `docs/usage.md` 的后续扩展清单中列出**，避免团队后续忘记企业门户首页通常也需要这两类数据 |
| OG 图片                        | 占位必做  | 提供默认图片路径，不接动态生成服务                                                                                                                                                           |

`robots.txt` 规则：

- `production` 环境默认允许索引。
- 非 `production` 环境默认 `Disallow: /`。
- `Sitemap` 地址从 `runtimeConfig.public.siteUrl` 生成。
- 不在 robots 中硬编码真实业务域名。

`sitemap.xml` 数据来源：

- 静态公开页面来自 `config/seo.ts` 或 `config/site.ts` 的页面清单。
- 新闻详情页来自 `app/data/news.ts`。
- 多语言 URL 由 i18n 配置和统一 locale path 工具生成。
- 404、预览页、登录页、内部页面不进入 sitemap。

### 5.4.1 routeRules 和渲染策略

目标：

- 用 Nuxt `routeRules` 明确哪些页面预渲染、哪些 SSR、哪些缓存。
- 官网/营销页优先减少运行时成本；需要实时数据的页面保留 SSR。
- 生产缓存策略写在配置里，不散落在页面中。

> **核对说明：** 下方 `prerender`/`swr`/`cors`/`redirect` 的用法已与官方文档核对一致（已核对：https://nuxt.com/docs/4.x/guide/concepts/rendering）。

推荐配置示例：

```ts
export default defineNuxtConfig({
  routeRules: {
    "/": { prerender: true },
    "/pricing": { prerender: true },
    "/help": { prerender: true },
    "/en": { prerender: true },
    "/en/pricing": { prerender: true },
    "/en/help": { prerender: true },
    "/news/**": { swr: 3600 },
    "/en/news/**": { swr: 3600 },
    "/api/**": { cors: true },
    "/old-page": { redirect: "/pricing" },
  },
});
```

v0.1 默认策略：

| 路由           | 策略                        | 原因                         |
| -------------- | --------------------------- | ---------------------------- |
| `/`            | `prerender: true`           | 首页内容示例稳定，适合静态化 |
| `/pricing`     | `prerender: true`           | 价格页示例稳定，适合静态化   |
| `/help`        | `prerender: true`           | FAQ 示例来自 typed 本地数据  |
| `/en`          | `prerender: true`           | 非默认语言首页也要验证 SEO HTML |
| `/en/pricing`  | `prerender: true`           | 非默认语言价格页与默认语言策略一致 |
| `/en/help`     | `prerender: true`           | 非默认语言帮助页与默认语言策略一致 |
| `/news/[slug]` | `swr: 3600`                 | 展示内容详情页缓存策略       |
| `/en/news/[slug]` | `swr: 3600`              | 非默认语言详情页也进入缓存策略 |
| `/api/**`      | `cors: true` 或按需 headers | 统一 server route 边界       |
| `/[[language]]/[...slug]` | SSR 404                     | 保证状态码和多语言错误页正确 |

多语言 routeRules 规则：

- routeRules 必须覆盖默认语言 canonical URL 和非默认语言短前缀 URL，不能只覆盖 `/pricing` 而遗漏 `/en/pricing`。
- `sitemap.xml`、`hreflang`、`canonical` 和 routeRules 使用同一份公开页面清单，避免 SEO 产物和实际渲染策略不一致。
- 默认语言短前缀 `/zh/*` 只负责 301 归一化，不作为 prerender 或 sitemap 的目标 URL。
- 新增公开页面时，必须同步更新页面清单、routeRules、sitemap 和多语言 alternate 测试。

验收标准：

- `nuxt.config.ts` 明确写出 v0.1 routeRules。
- `nuxt.config.ts` 明确写出默认语言和非默认语言的 v0.1 routeRules，或者由测试覆盖的页面清单生成这些规则。
- README 解释 SSR、prerender、SWR 的使用边界。
- 示例页面能证明首屏 SEO 内容在 HTML 中存在。
- 404 页面能返回正确状态码，不只是客户端兜底跳转。

### 5.5 布局模块

| Layout    | 用途                             |
| --------- | -------------------------------- |
| `default` | 官网常规页面，包含 Header/Footer |
| `empty`   | 错误页、嵌入页、极简页           |

后续如果启用 auth 模块，再增加 `auth` layout 作为登录/注册页壳。

`default` layout 只做通用导航：

- 可选登录/用户入口
- Footer

不放入：

- 会员弹窗
- 支付弹窗
- 具体业务跳转
- 具体广告逻辑
- 具体活动逻辑

验收标准：

- layout 可以被新项目直接复用。
- 项目特定导航通过 `config/nav.ts` 配置。
- Header/Footer 不依赖业务 store。

### 5.5.1 错误页模块

v0.1 同时提供 Nuxt 全局错误页和路由兜底页：

| 文件                      | 职责                                                               |
| ------------------------- | ------------------------------------------------------------------ |
| `app/error.vue`           | 处理 Nuxt/Nitro 抛出的全局错误，如 SSR 500、服务端异常、未捕获错误 |
| `app/pages/[[language]]/[...slug].vue` | 处理没有匹配到的业务路由，作为多语言 404 页面兜底                  |

错误页规则：

- 404 页面必须设置正确 HTTP status code。
- 500 页面不暴露服务端异常细节。
- 404、500 默认 `noindex`。
- 错误页文案走 i18n，不硬编码单语言。
- `app/error.vue` 可以使用 `clearError({ redirect: '/' })` 返回首页。
- `pages/[[language]]/[...slug].vue` 不做客户端假跳转，优先让服务端返回正确 404。

验收标准：

- 创建 `app/error.vue`。
- 创建 `app/pages/[[language]]/[...slug].vue`。
- 访问不存在路径时返回 404 状态码。
- SSR 抛错时能进入 `app/error.vue`。
- 错误页接入 `usePageSeo` 或专用 `useErrorPageSeo`，并默认 `noindex`。

### 5.6 登录模块

登录模块不进入 v0.1 默认闭环，只保留后续扩展方案，不绑定具体登录供应商。

**v0.1-core 的处理方式（本次修复）：** 不创建 `stores/auth.ts`、`composables/useAuth.ts`、`middleware/auth.ts` 这类运行时代码占位。原因是“空实现”在模板里很容易被误认为已支持登录，反而制造隐性业务债。v0.1-core 只在 `docs/usage.md` 写清楚后续 auth 模块接入契约。

后续启用 auth 模块时，建议新增：

```txt
app/stores/auth.ts
app/composables/useAuth.ts
app/middleware/auth.ts
app/layouts/auth.vue
```

`auth` store 建议只维护通用状态：

```ts
interface AuthState {
  user: UserInfo | null;
  token: string | null;
  initialized: boolean;
}
```

后续启用 auth 模块时的验收标准：

- 未登录跳转逻辑集中在 `middleware/auth.ts`。
- 登录 token 读写集中在 `useAuth`。
- 具体 Google/Facebook/邮箱登录作为业务模块接入，不进核心骨架。
- auth 模块必须作为独立任务提交，并补充对应单测和集成验证，不允许混入 v0.1-core。

### 5.7 埋点模块

analytics 埋点模块不做。

规则：

- 不创建 `useAnalytics.ts`、`analytics.client.ts`、`config/analytics.ts`。
- 不内置 GTM、Clarity、GA 或任何真实第三方投放 ID。
- 不在 `app.head` 或 plugin 中预留第三方脚本加载逻辑。
- UTM 保留、页面事件上报、投放平台接入都不进入本计划。

### 6.1 部署策略

v0.1 默认部署目标是 Nitro `node-server`。原因是它能完整覆盖 SSR、server/api、runtimeConfig、routeRules、错误状态码和中间件能力，适合作为 starter 的第一条可靠路径。

部署矩阵：

| 部署方式           | v0.1 状态 | 适合场景                                       | 注意事项                                                       |
| ------------------ | --------- | ---------------------------------------------- | -------------------------------------------------------------- |
| Node server        | v0.1-core 默认支持       | SSR 官网、轻 SaaS 前台、需要 server/api 的项目 | 生产环境通过进程管理器、容器或平台注入 `NUXT_*`                |
| Docker + Nginx     | v0.1-core 默认验证路径   | 团队自托管、容器化部署                         | v0.1 必须提供样例文件，并完成镜像构建、容器启动和 Nginx 反代验证 |
| Vercel             | 文档说明                 | 需要快速托管和边缘能力的海外站                 | 需要单独验证 preset、运行时环境变量和缓存行为                  |
| Cloudflare         | 文档说明                 | Edge 部署、全球访问优化                        | Node API、依赖包兼容性需要逐项验证                             |
| Static / prerender | 文档说明                 | 纯静态营销页、无 server/api 的内容站           | 使用 server/api、运行时 SSR、私有 runtimeConfig 时不适合纯静态 |

Node server 最小生产运行约定：

```bash
pnpm build
node .output/server/index.mjs
```

Docker + Nginx 默认部署形态：

```txt
Browser
  -> Nginx
    -> Nuxt node-server container
```

文件约定：

| 文件                 | 职责                                                              |
| -------------------- | ----------------------------------------------------------------- |
| `Dockerfile`         | 构建 Nuxt node-server 镜像，运行 `.output/server/index.mjs`       |
| `.dockerignore`      | 排除 `node_modules`、`.nuxt`、`.output`、日志、环境文件等无关内容 |
| `deploy/nginx.conf`  | 提供基础反向代理和静态资源缓存示例                                |
| `docs/deployment.md` | 解释 Docker 构建、运行、环境变量注入、Nginx 反代边界              |

Dockerfile 规则：

- 使用多阶段构建，安装依赖、构建、运行分层。
- 生产镜像只包含运行 Nuxt server 必要文件。
- 不把 `.env.prod`、密钥、真实证书复制进镜像。
- 容器运行时通过 `NUXT_*` 注入环境变量。
- 默认监听 `3000`，由 Nginx 反向代理到容器。

Nginx 规则：

- `/` 反向代理到 Nuxt node-server。
- `/_nuxt/` 静态资源启用长缓存。
- 传递 `Host`、`X-Forwarded-For`、`X-Forwarded-Proto`。
- gzip 可以在 Nginx 层开启；brotli、HTTPS、证书按实际基础设施决定。
- Nginx 不承载业务路由逻辑，业务路由仍由 Nuxt/Nitro 处理。

生产环境变量由运行环境提供：

```txt
NUXT_PUBLIC_APP_ENV=production
NUXT_PUBLIC_API_BASE=https://api.example.com
NUXT_PUBLIC_SITE_URL=https://example.com
NUXT_API_SECRET=server-only-secret
```

v0.1-core 验收标准：

- README 提供 Node server 部署说明。
- 提供 `Dockerfile`、`.dockerignore`、`deploy/nginx.conf` 的基础示例。
- Docker 镜像能构建成功，并默认运行 `.output/server/index.mjs`。
- Nginx 能反代访问 Nuxt node-server，`/_nuxt/` 静态资源缓存规则生效。
- 文档记录镜像构建、容器启动、Nginx 反代验证命令。
- README 说明 Vercel、Cloudflare、static/prerender 是后续可验证路径，不作为 v0.1 默认承诺。
- `pnpm build` 后的 `.output/server/index.mjs` 能作为默认启动入口。
- 文档明确：使用 server/api 或私有 runtimeConfig 时，不应直接当作纯静态站交付。

### 8.3 安全、性能和可访问性基线

v0.1 不做复杂安全平台，但要有基础约束：

- server/api 不向客户端返回密钥、token、cookie、完整堆栈和内部服务地址。
- 第三方脚本必须通过配置启用，默认关闭，且不能写入真实 ID。
- Cookie 相关示例必须说明 `HttpOnly`、`Secure`、`SameSite` 的使用边界。
- README 说明 CSP、HSTS、HTTPS、WAF 等由生产基础设施按项目补齐。
- 日志示例必须脱敏 authorization、cookie、token、secret、password。
- **SSR 外部请求的 header 转发白名单机制（见 5.2 节）视为安全基线的一部分，不是可选优化。**

性能和体验基线：

- 示例页面图片必须有明确尺寸或响应式约束，避免明显 CLS。
- 首屏关键内容必须来自 SSR HTML，不依赖客户端 mounted 后才出现。
- 字体、图片、第三方脚本加载策略写入 `docs/conventions.md`。
- 主要页面在移动端和桌面端都可读、可点击、无明显横向溢出。
- 基础交互元素具备可访问名称，导航和语言切换可键盘访问。

## 10. 从当前 `aippt-home` 提炼时的迁移建议

参考原则：

- `aippt-home` 是生产经验样本，不是最佳实践模板。
- 已经被真实业务验证、且能脱离具体业务复用的做法，可以吸收。
- 历史包袱、临时方案、强业务耦合、重复封装、写死配置，应该借鉴问题背景，但用更优方案重做。
- 每个能力迁移前都要回答两个问题：这个能力解决的是通用问题吗？它现在的实现方式是不是仍然是最佳选择？

可以借鉴：

- `runtimeConfig.public.apiHost/env/baseUrl` 的环境配置思路。
- `utils/request.ts` 中 SSR 和客户端请求分流的经验。
- `nitro.devProxy` 的开发期代理经验（配置项已在 Nitro config 文档核对），但必须明确生产环境由网关、Nginx、CDN、Ingress 或 BFF 接管路由。
- `apis/*.ts` 的接口分层经验，将接口定义从页面中抽离出来，统一管理请求 key、路径、入参和返回类型。
- `middleware/default.global.ts` 中语言前缀校验、尾斜杠清理、默认语言重定向的思路。
- `i18n/index.ts` 中默认语言不带前缀、多语言 path 生成的业务经验。
- `error.vue` 和 `pages/[[language]]/404.vue` 的错误页经验，沉淀多语言 404、服务端状态码和客户端兜底跳转策略。
- `layouts/default.vue` 的 Header/Footer 结构，但只能保留结构，不保留业务逻辑。
- `app.head` 中多平台投放脚本、`saveUtmParams(route.query)`、`scripts/vite-oss-url-plugin.ts` 只作为“不要照搬业务耦合”的反例，不进入本计划。

建议增强模块：

| 模块                | 从 `aippt-home` 吸收的生产经验                   | 骨架中的落地方式                                                                  |
| ------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------- |
| dev-proxy           | 本地浏览器请求走同源路径，SSR 请求直连 `apiHost` | `nitro.devProxy` 只用于开发，并在文档中声明生产路由边界；实施时以 Task 0 的版本验证结果为准 |
| api-layer           | `apis/*.ts` 统一封装后端接口                     | 建立 `app/apis` 或 `shared/apis`，页面禁止直接散写 URL                            |
| error-pages         | `error.vue` 兜底到多语言 404 页面                | 建立 `error.vue`、`pages/[[language]]/[...slug].vue`、`useErrorPageSeo`           |
| route-normalization | 去尾斜杠、默认语言重定向、非法语言拦截           | 建立 `locale.global.ts` 和 `route-normalize.global.ts`                            |

需要升级为更优做法：

| `aippt-home` 中的现状                                              | 不直接照搬的原因                           | starter 中的推荐做法                                           |
| ------------------------------------------------------------------ | ------------------------------------------ | -------------------------------------------------------------- |
| `nuxt.config.ts` 中写入大量第三方脚本和真实 ID                     | 全局配置过重，品牌和投放平台强绑定         | 不接入 analytics，不写第三方投放脚本                         |
| 同时存在 `utils/request.ts` 和 `hooks/use-request.ts` 两套请求封装 | 调用入口分裂，团队容易混用                 | 只保留一个 `useApi`，覆盖 SSR 和客户端交互请求                 |
| `app.vue` 承担 UTM、埋点、地区、登录回调、活动逻辑                 | 应用入口过重，初始化逻辑和业务逻辑混在一起 | `app.vue` 只保留应用壳，初始化逻辑拆到 plugin/composable       |
| `layouts/default.vue` 强依赖会员、支付、模板、SDK                  | layout 变成业务容器，复用成本高            | layout 只做 Header/Footer/导航壳，业务入口通过配置和 slot 接入 |
| `scripts/dev.mjs` 会改 `.env` 和 `.gitlab-ci.yml`                  | 本地启动脚本有副作用，容易污染工作区       | 环境切换通过明确 npm scripts 和 `.env.*` 文件完成              |
| `app.head` 统一注入所有平台脚本                                    | 不同环境、国家、页面可能需要不同加载策略   | 不接入 analytics，避免模板默认带投放脚本                     |
| CDN/OSS 上传逻辑写成项目专用插件                                   | 云厂商和路径强绑定                         | 上传和 deployment-assets 不进入本计划                         |

必须剥离：

- AiPPT 品牌文案和域名。
- 投放脚本真实 ID。
- 新用户折扣、会员、支付、积分。
- 模板站、工具页、工作台跳转等具体业务。
- `@isheji/*` 私有 SDK 强依赖。
- 会修改 `.gitlab-ci.yml` 的本地启动脚本。
- 页面级大量业务 API。

提炼方式：

1. 先新建干净 starter，不在原项目里直接删业务。
2. 把通用能力按模块迁移，而不是复制整个文件。
3. 每迁移一个能力，就补一段 README 用法。
4. 每迁移一个能力，就跑一次 build。

## 11. 首版交付标准

v0.1-alpha 完成后，应满足：

- 新项目能执行 `pnpm install && pnpm dev` 跑起来。
- `pnpm build` 通过。
- 首页、价格页、帮助页、新闻列表、新闻详情样板、404 页能访问。
- 默认语言和英文短前缀主链路可用。
- layout、SEO 入口、多语言路径、基础主题、示例数据主链路可演示。
- README 有快速启动、目录说明和当前已知限制。

v0.1-core 完成后，应满足：

- 新项目 clone 后，**执行 `pnpm install && pnpm dev` 可在 30 分钟内跑起来**（这条不包含完整质量门禁的执行时间，完整门禁耗时另计，见下方）。
- 已提交的 `.env.dev` 能跑通 dev。
- 至少有首页、价格页、帮助页、新闻列表、新闻详情样板、404 页。
- 支持默认语言和一个非默认语言；默认语言无前缀、非默认语言有前缀、默认语言短前缀重定向由自研路由层实现并验证。
- 有统一请求入口。
- `useApi` 有稳定 key 规则、SSR payload 复用、header 白名单和错误脱敏约束，且有测试验证白名单外 header 未被转发。
- 有 Pinia 接入、通用 `app` store 和 `theme` store；没有 auth store、auth middleware、auth composable 运行时代码占位。
- 有 light/dark design token、CSS variables、Ant Design Vue token 映射和主题切换入口，刷新后能保持用户选择。
- 有清晰的 `runtimeConfig`、`app.config.ts`、`config/*.ts`、`config/theme.ts` 职责边界。
- 关键公开运行时配置缺失时，有明确降级或报错规则。
- 有统一 SEO 入口，并能生成 `robots.txt` 和 `sitemap.xml`。
- SSR HTML 中能看到公开页面核心内容和 SEO 基础标签。
- 有 v0.1 routeRules，覆盖 prerender、SWR、SSR 404 的基本策略。
- 有 `app/error.vue` 处理全局错误，`app/pages/[[language]]/[...slug].vue` 处理路由 404。
- 不存在路径返回 HTTP 404，不只是页面显示 404 文案。
- 有 default/empty 两种 layout。
- 有 `.nvmrc`、`.node-version`、`packageManager` 字段锁定 Node/pnpm。
- 有 `pnpm-lock.yaml`，README 记录已验证的 Node、pnpm、Nuxt 和主要模块版本。
- 有 Docker + Nginx 的 node-server 部署样例文件，并完成 Docker build/run 与 Nginx 反代验证。
- README 明确本地 `.env.*` 与生产 `NUXT_*` 的区别。
- README 明确 Node server 是 v0.1 默认部署方式。
- README 明确远程 CI 不进入本计划。
- README 或 usage 明确常见裁剪路径和裁剪后的验证命令。
- 没有任何真实业务品牌和投放 ID。
- 没有 token、cookie、secret、password、真实第三方 ID 泄露到客户端代码、日志示例或文档。
- `pnpm lint`、`pnpm format:check`、`pnpm stylelint`、`pnpm typecheck`、`pnpm test`、`pnpm build`、`pnpm docker:build` 全部通过，并完成 Docker 容器启动和 Nginx 反代验证（这套完整 v0.1 验证的耗时不计入上方"30 分钟"口径）。
- husky 的 `pre-commit` 和 `commit-msg` hook 可正常执行。

## 12. 不做事项

首版不做：

- 内部 CLI scaffold。
- analytics 埋点模块。
- CMS 接入、CMS 后台、内容模型和发布流程。
- Playwright E2E。
- 真实支付模块。
- 真实会员模块。
- 默认登录模块，包括 auth store、auth middleware、auth composable 这类运行时代码占位。
- 默认埋点平台和真实第三方脚本 ID。
- 复杂 CSP/权限/风控平台。
- 真实上传模块。
- 更多语言。
- 复杂后台权限。
- 多 UI 框架同时完整维护。
- 大而全的业务组件库。
- 远程 CI 流水线（GitHub Actions 或等价工具）。

以上能力不进入当前计划；如果未来某个业务项目单独需要，应在业务项目中独立设计，不作为 `nuxt-modern-starter` 的 0.1 交付内容。

## 13. 推荐执行顺序

v0.1-core 最小可用闭环：

```txt
Task 0 -> Task 1 -> Task 2 -> Task 3 -> Task 4 -> Task 5 -> Task 6 -> Task 7 -> Task 8 -> Task 9 -> Task 10 -> Task 11
```

如果项目需要登录，在 v0.1-core 完成后再新增 auth 可选模块任务，不混入首版闭环。

## 14. 最终建议

建议第一阶段做 GitHub template，不做 CLI。

原因：

- 成本低。
- 团队容易理解。
- 能快速在真实项目里验证。
- 后续重复使用 2-3 次后，再抽象 CLI 更稳。

首版目标：

```txt
nuxt-modern-starter v0.1
```

首版只解决基础问题：

- 项目能启动。
- 页面能写。
- SEO 有统一规范。
- 多语言路径不乱。
- 请求不分裂。
- 环境配置不散。
- layout 不带业务债。

这个边界最实用，也最不容易失控。
